## Decision and purpose

Package the existing open-todo React application in Tauri, with macOS as the first verified desktop platform and a cross-platform project structure from day one. Preserve the browser application and one shared implementation of task behavior.

The owner explicitly narrowed the sequence: “Io comincerei solo a mettere l'app dentro tauri, poi pensiamo alle feature desktop.” Platform direction: “prima macos, ma nasce per essere universale.” Approach A was selected explicitly.

This extends the historical web-only platform decision; it does not replace the static web application or introduce an application server/proxy. Universal means cross-platform intent here, not an Apple universal binary or verified Windows/Linux support.

## Scope

- Add a minimal Tauri shell loading the locally bundled Vite application in production. Development may use the existing Vite server.
- Use standard window decorations and the existing UI, brand and theme. No custom macOS-only layout or desktop service abstraction framework.
- Provide documented desktop development and local macOS build commands without changing existing web commands.
- Preserve server setup, supported authentication methods, navigation, task behavior and explicit error handling.
- Keep VERSION as the source of truth for desktop and web version claims; integrate desktop metadata into version synchronization/checking rather than creating an independently maintained version.
- Isolate genuinely platform-specific configuration. Do not introduce macOS-specific assumptions into shared task/API code.
- **D2, approved during CEO review:** persist window size and position using Tauri's official window-state plugin, without changing the shared React layout. Restore a visible, usable window when displays change or stored geometry is invalid. Verify first launch, normal restart, disconnected external monitor, corrupt/missing saved state and failed persistence. A persistence failure must not prevent the window from opening; use safe default geometry and a credential-free diagnostic. Plugin availability is documented for macOS/Windows/Linux; actual behavior is not yet tested.

**D6, approved during CEO review:** responsive behavior is now in this slice, explicitly superseding its earlier deferral. Implement the collapsible sidebar and adapt narrow layouts in shared React/CSS so both browser and desktop benefit. Cover lists, task detail, quick-add, setup/login and dialogs; do not treat sidebar hiding alone as completion. Derive breakpoints from content fit using shipped tokens and verify keyboard/focus behavior, scrolling, long text, zoom and resizing with an active draft. Define supported minimum viewport dimensions through testing, rather than preserving the current desktop-only geometry with a large minimum window size. **D7, owner-selected reference:** reproduce Todoist's responsive navigation behavior rather than inventing an alternative. The owner-provided screenshot shows the narrow-state sidebar overlaying the content, a dimmed backdrop, and a panel-toggle icon at the top. Do not use an always-visible icon rail. Retain open-todo's original icons, teal brand, and existing destinations; screenshot-only features such as notifications, reports and teams are not scope additions. The screenshot does not establish the breakpoint, transitions, Escape/backdrop behavior, focus handling or wide-state preference restoration: measure these in the live reference before claiming parity, and label any unobserved behavior as an implementation design choice. Do not copy account/task content or proprietary assets into repository documentation.

Not in this slice: notification delivery, tray/background services (except the macOS process lifecycle approved in D4), global shortcuts, offline replicas/outbox, OIDC, auto-update, public installers, signing/notarization, and Windows/Linux release validation. Existing reminder editing remains existing functionality; it does not imply desktop notification delivery.

## Approved desktop lifecycle additions

- **D3, approved during CEO review:** one running application process and one main window for this slice. A subsequent launch must show, unminimize when necessary, and focus the existing main window, without creating a second process or resetting the current view/session. Use the official single-instance plugin, registered first as its documentation requires. This plugin prevents duplicate processes, not duplicate windows; enforce the main-window behavior separately. Test simultaneous launches, an already-visible window, a minimized window, and Dock reopening. If the process survives closure of its last window, reopening must recreate the main window safely; it must not panic because the window handle is missing. Surface activation failures through credential-free diagnostics. Close-versus-quit policy is defined by D4 below.
- **D4, approved during CEO review:** on macOS, closing the main window leaves the application process running without a window. Dock reopening or a subsequent launch recreates the main window if absent, or activates it if present. Command-Q explicitly quits. This is a narrow exception to the background-operation non-goal: no tray, notification scheduler, or new background polling service is included. Verify close → Dock reopen, close → second launch, repeated reopen events (one main window), and Command-Q → fresh launch. Recreating the UI preserves persisted server/session settings and D2 geometry; it does not promise persistence of unsaved task drafts. Non-macOS lifecycle behavior must be documented when those platforms are implemented and tested.

- **D5, approved during CEO review:** guard voluntary window close and application quit against loss of changed, unsaved drafts. Offer cancel or explicit discard; cancelling leaves the editor and text intact. While a save is pending, defer destructive closure until its outcome; on failure retain the draft and visible error instead of closing. Cover every existing draft-bearing surface, not only task descriptions, and test close/quit, repeated close requests, save success/failure, and edits made while awaiting a result. Reuse existing dirty/pending signals where available; introduce no automatic save or crash-recovery persistence. This qualifies D4: window destruction is permitted only after the guard allows it. Forced termination and OS crashes are outside this protection.

## D10 — Token verification errors (approved repair)

Fix the existing shared SetupScreen token-login catch branch: accept a successful `/user` probe, reject 401, and retain the existing explicitly identified HTTP 403 exception for scoped tokens. Do not treat network/CORS failure, 5xx, malformed responses or other exceptions as successful verification. Keep the login form and candidate input available with an actionable error and retry; do not persist the candidate or switch into the application on these failures. Add focused tests for success, 401, 403, network rejection, 5xx and invalid response parsing. A 403 is the preserved limited-token exception, not proof of access to task endpoints. The existing defect is confirmed by `src/screens/SetupScreen.tsx` lines 163–169; no desktop runtime test has run yet.

## D11 — Transport policy (approved)

HTTPS remains the default. Support explicitly configured HTTP instances with a clear unencrypted-connection warning and affirmative confirmation before sending credentials. Bind any remembered acknowledgement to the chosen server origin; changing servers must not reuse consent for a different origin. Apply the check at credential transmission, including stored-session startup, not only initial setup. Cover password/TOTP and API-token flows. Never disable HTTPS certificate validation. Verify actual HTTP and HTTPS behavior in the packaged macOS WebView; CSP permission, server CORS and OS transport rules are separate constraints. If supporting the approved policy requires a different transport boundary, return with measured evidence before adding a native HTTP bridge. Do not silently downgrade HTTPS to HTTP.

## D12 — Persistence failures (approved repair)

Expose persistence success/failure from the shared persistent-value layer instead of silently swallowing writes and removals. Critical consumers (server, token and transport acknowledgement) must report failed durability without claiming that restart persistence succeeded. Logout ends the current in-memory session even if storage removal fails, but shows that persistent removal failed and does not claim full success. Preserve noncritical preference fallback without unnecessarily blocking the application. Test blocked storage access, quota/write failure, removal failure, retry and a new consumer after simulated restart. No keychain migration is authorized. Existing failure paths are in `src/store/persistentValue.ts` lines 37–56.

## D13 — Pending-save escape hatch (approved)

Qualify D5's pending-save wait: show an explicit waiting state and offer staying in the app or exiting anyway with a warning that the server-side outcome may be unknown and the local draft may be lost. A voluntary force-exit choice is not cancellation/rollback of a remote write. Do not automatically retry mutations on reopen; read the server afresh. Test a never-settling request, server commit followed by lost response, repeated close/quit events, success/error racing with the user's exit choice, and absence of duplicate submissions. The same close-attempt state machine must serve window close and Command-Q. This does not introduce a general HTTP-timeout policy.

## Chosen architecture

```text
Web browser -------------------+
                               +-- Shared React application -- Vikunja API
Tauri window + bundled assets -+
```

Start with the existing API and storage paths, subject to a packaged-app verification. Do not preemptively add a native HTTP bridge, keychain migration, local proxy, or broad capabilities. The diagram is the intended architecture, not evidence that WebView networking already works.

Use the current stable Tauri major after checking official integration/security documentation during implementation. Native capability access should be minimal and explicitly justified. Load only bundled application content in the privileged window; remote navigation and external links need an explicit safe policy.

## Mandatory verification and decision boundaries

1. **Packaged networking:** verify the actual production WebView origin, CORS requirements, authentication headers and server connectivity. Development-server success is insufficient. Check the documented supported server URL policy, including whether plain HTTP is supported; never solve TLS errors by disabling certificate verification.
2. **Credentials:** verify persistence across restart, logout removal and storage separation from the browser. Do not promise automatic session import or OS-keychain protection. Record the retained web-storage security trade-off explicitly. If packaging requires a materially different credential or transport mechanism, return with a focused decision before expanding scope.
3. **Permissions and navigation:** inspect effective capabilities and content security policy. Avoid blanket native permissions or arbitrary remote pages in a privileged window.
4. **Lifecycle:** verify launching, closing, reopening and quitting on macOS, including Dock behavior. No promise of reminders or polling while the app is closed. Confirm foreground freshness resumes after hide/show or sleep/wake; report discrepancies rather than silently losing updates.
5. **Versioning:** demonstrate that changing VERSION drives the desktop artifact/version metadata as well as the web version, and that drift checks reject disagreement.
6. **Cross-platform intent:** use portable paths and shared configuration. Document Windows/Linux as not yet verified. Do not claim cross-platform runtime support based solely on portable source.

Implementation requires current-code inspection and official Tauri documentation checks. This session did not run a Tauri build, desktop security review, network probe or cross-model review.

## Success criteria

- A local macOS build launches the bundled application without a running Vite server.
- Server setup and the existing supported login flows work, or a concrete blocker is reported before declaring completion.
- Restart preserves intended settings/session state; logout removes the session.
- Lists, task detail, quick-add, completion and representative edits behave as in the web application. Live write tests require explicit authorization and scratch tasks.
- Connection/authentication failures are visible and actionable; no blank window or silent failure.
- Closing, reopening, quitting and returning from suspension have documented, tested behavior.
- Existing web checks/tests/build remain green; desktop build/version checks are added as appropriate.
- Only individually approved requirements in D2–D13 extend or clarify the initial scope; responsive behavior works in both web and desktop, with no clipped essential controls at supported widths.

### Competing operations and assertions

| Ordering | Required result |
|---|---|
| Save starts → close requested → save succeeds | One mutation, guarded closure proceeds once |
| Save starts → close requested → save fails | Window stays open with draft and error |
| Close guard shown → user cancels → save completes | Cancellation remains effective; no stale close callback destroys the window |
| Close guard shown → another edit occurs | Check current dirty/pending state before destruction; do not use the earlier snapshot as permission |
| Close pending → repeated close/quit/reopen events | One coherent guard; at most one main window, no duplicated mutation |
| User chooses exit-anyway → late response | No callback recreates a closed window or resubmits; next launch reads server state |
| Storage removal fails → next consumer starts | Failure was visible; no claim of durable logout; test actual retained-storage behavior |
| Resize crosses navigation breakpoint → editor is active | Draft remains intact and focus stays usable; layout does not remount the editor |

## Engineering review E2 — Native close coordinator (approved)

Use one small Rust-owned lifecycle coordinator for both main-window close and application exit requests. Prevent the native default before requesting a frontend decision. React owns dirty/pending state and user confirmation; it does not own a second competing native close policy. Correlate every decision with the active close-attempt ID and window generation, discard stale/duplicate responses, and authorize exactly one matching close or quit. Re-read current frontend dirty/pending state before authorization. An intentional final close/exit needs a one-use bypass to avoid recursing through the same guard. With no main window, application quit must not wait for a nonexistent frontend. With an existing but unresponsive frontend, never interpret silence as a clean editor: provide a visible native recovery choice, including explicit exit with possible loss, rather than silently destroying the window. Native errors and recovery diagnostics contain no credentials/draft content. Test close versus quit, startup before frontend readiness, absent window, repeated requests, cancellation, late responses, save outcome races and listener cleanup/remount. Use Tauri's actual WindowEvent/RunEvent APIs; `destroy()` bypasses close-request handling and must remain behind the coordinator's authorization. No restart/updater flow is in scope.

### Native handshake and failure paths

```text
Native request(kind=close|quit)
  -> prevent default
  -> register attempt ID / window generation
  -> frontend ready?
       absent window + quit -> exit directly
       existing window, not ready/unresponsive -> visible native recovery
       ready -> inspect current drafts + pending writes
                  cancel -> invalidate attempt
                  clean/discard -> authorize matching attempt once
                  pending -> wait or explicit exit-anyway

Frontend decision arrives
  stale ID / generation / already consumed -> ignore, no window destruction
  current decision but new dirty/pending work -> reevaluate before authorization
  valid authorized decision -> close/exit with one-use recursion bypass
```

The existence of an ID is not proof of race safety. Tests must pause at message delivery and save completion, then vary ordering. Native coordinator tests cover wrong generation, duplicate messages, cancellation and missing frontend; packaged tests verify that real Command-Q reaches the same policy. A frontend event listener alone is not accepted as coverage for application exit.
